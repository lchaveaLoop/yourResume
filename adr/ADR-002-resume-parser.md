# ADR-002: 简历解析方案

## Status
Accepted

## Context
简历输入格式为 .docx 和 .md，需要统一转换为结构化 JSON 数据。
两种格式的解析难度不同：
- **Markdown**: 结构化文本，正则解析即可
- **docx**: 二进制 OOXML 格式，区块识别需要分析 XML 结构

## Decision

### Markdown 解析：前端自定义解析器（正则 + 行级状态机）

```
解析策略：
- 一级标题 (#) → 姓名
- 二级标题 (##) → 区块标题（教育/工作/项目/技能）
- 列表项 (- / 1.) → 列表内容
- 空行 → 区块分隔
- 多行连续内容 → 合并为详情文本
```

**优势**: 零依赖，部署简单，MVP 阶段完全够用

### docx 解析：后端 python-docx + 智能区块识别

```
解析策略：
1. 遍历所有 <w:p> 段落元素
2. 读取 paragraph.style.name 判断是否为标题段落
3. 遇到标题时，将之前内容归组到当前区块
4. 区块识别关键词匹配（中英文）
5. 输出标准 JSON 结构
```

**后端理由**:
- python-docx 是处理 docx 的标准方案，稳定可靠
- OOXML 内部解析复杂，前端难以维护
- 保持解析逻辑与前端解耦，便于后续 AI 增强

### 备选：前端 jszip 解析 docx
- 如果后端部署成本过高，可切换为前端方案
- 使用 jszip 解压 docx（ZIP 格式），再用 DOMParser 解析 XML
- **风险**: 代码量增加，边缘 case 处理复杂

## Consequences

### Positive
- MD 解析零依赖，前端实现简单
- docx 后端解析稳定可靠，覆盖复杂表格/样式
- 统一输出 JSON 结构，前端渲染层完全解耦

### Negative
- 需要维护两套解析器
- docx 格式多样性（不同模板、不同写法）可能导致识别率问题
- 后端引入增加了部署复杂度

### Neutral
- 解析质量取决于简历格式规范程度
- 非标准格式简历可能需要人工兜底

## Alternatives Considered

### 方案 B：纯前端 docx 解析（jszip + DOMParser）
- 优点：无需后端，部署最简
- 缺点：XML 解析代码量大，样式继承难以处理，边缘 case 多
- **未选**: 维护成本过高

### 方案 C：云解析 API（阿里/腾讯 OCR）
- 优点：支持扫描件、图片简历
- 缺点：需要账号付费，隐私顾虑，延迟高
- **未选**: MVP 阶段过度设计

### 方案 D： mammoth（docx → HTML）
- mammoth 是成熟的 docx 转 HTML 库
- 优点：处理样式继承更好
- 缺点：转 HTML 后还需二次解析为 JSON，转换成本高
- **待评估**: 可作为进阶优化方案
